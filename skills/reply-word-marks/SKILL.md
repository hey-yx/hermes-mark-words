# 回复末尾的词标记块（::hmw）

hermes-mark-words 插件会给回复里有疑点的词加标记：普通疑点是中性点线，疑似生造或含义不明是细红波浪线，鼠标悬停能看到解释和追问。标记关系由你在这条回复里直接写出来，插件不再另外请求模型。

## 什么时候写

三条都满足才写：

1. 这是 Hermes 桌面端聊天里给用户看的最终回复（环境段写着 Platform: desktop）。
2. 正文里确实有读者会存疑的词，下面这类占一条就算：
   - 疑似生造、可能不存在的说法；
   - 含义不明、用法有歧义，或者你自己临时造出来的概念；
   - 值得追问核实的说法里的关键词。
3. 这条回复本身就是给用户看的正文。

只标有疑点的，不标术语表。基本口径：

基础词、常识词、行业通行的标准术语不要标，浏览器、下载、缓存、接口、API、数据库、p90、TTFB 这些意思明确的都算，哪怕它技术性很强。加载、路由、同步、备份、日志、部署、监控这类常规工程词同样不标。

两字纯汉字词只有「疑似生造」和「含义不明」两档能标，插件闸门会拒掉术语档的两字词。真想标两字词，就把疑点写进 kind。

正文里已经解释清楚的词不标。文件路径、命令、代码标识符、版本号、纯数字也不标。

一段回复通常 0 到 3 个词。一个够格的都没有，整块就不写，绝不凑数。

不限语言。回复是中文、英文、日文、韩文还是混着写，都按同一口径挑；term 原样取那个语言的写法。

这些都一律不写：非 desktop 平台（消息平台、CLI 管道、cron）、工具调用结果、被其他代理消费的中间产物（子任务总结、看板交接）、看板卡片、PR、issue、提交信息、文件内容、代码。

## 怎么写

正文写完后，末尾另起一段，跟正文空一行。每条指令单独成段，指令之间也必须空一行。宿主只把「整段就是一个 ::name{...}」的段落渲染成组件，两行指令挤在同一段里会被当成普通文字原样显示出来：

::hmw{term="原文里的连续片段", kind="unclear", explain="这个词在这段话里指什么、是干嘛用的、跟他有什么关系，60 字以内", note="不确定处或来源提示，没有就省掉本字段", q1="针对该词语境的具体追问"}

::hmw{term="第二个词", kind="fabricated", explain="…", q1="…"}

上面两条之间那个空行不是排版偏好。少了它，整块指令会直接出现在对话正文里。

term 逐字取自正文，含大小写和原文语言，2 到 24 字，不改写也不翻译。

kind 从 fabricated（疑似生造）、unclear（含义不明或有歧义）、term（用法不标准、值得商榷）里选一个。以存疑为主，term 只是兜底。

explain 要就着上下文回答「它在这段话里指什么、是干嘛用的、跟他有什么关系」，不写百科式定义。真从上下文看不出它指什么，就明说看不出，再讲哪里可疑，不要硬编。

属性值里不能出现双引号、花括号和换行。解释里引用别处的说法用「」。值本身带双引号，就改用单引号包住整个值。

q1、q2 是可选追问，针对这个词在这段语境里的疑点，要能落地核实。0 到 2 条都正常：只给一条也行，一条都不写也行。没有能落地的追问就别写 q 字段，绝不凑满两条。q3 仍然能解析，一般用不到。

每个词一条指令，最多 3 条，指令之间空一行。宁缺毋滥。

标记块必须是回复的最后一部分，块后面不再有任何文字。
